# ККМ, фискальные чеки и миграция из других CRM

Дата подготовки: 2026-05-17.

## Источники

- YooKassa: справочник значений для 54-ФЗ (`receipt.items`, `payment_subject`, `payment_mode`, `vat_code`, `tax_system_code`): https://yookassa.ru/developers/payment-acceptance/receipts/54fz/yoomoney/parameters-values
- T-Bank Kassa: оплата по 54-ФЗ, `Receipt`, `Items`, `Payments`, `Taxation`, `PaymentMethod`, `PaymentObject`: https://developer.tbank.ru/eacq/api/oplata-po-54-fz
- T-Bank Kassa: отправка закрывающего чека: https://developer.tbank.ru/eacq/api/send-closing-receipt
- СберБанк эквайринг: REST API с `orderBundle`/`cartItems` для фискальных позиций: https://securepayments.sberbank.ru/wiki/doku.php/integration:api:rest:requests:register_cart
- 54-ФЗ требует фискализировать не только сумму оплаты, но и реквизиты позиции: предмет расчета, способ расчета, ставку НДС, количество, цену, контакт покупателя для электронного чека.

## Что заложено в CRM

### Нормализованная модель чека

Внутренний формат не завязан на одного провайдера:

- `PaymentReceipt` - чек по платежу, статус, провайдер, СНО, тип оплаты, сумма чека, сумма текущего платежа, контакт покупателя, provider payload/response.
- `PaymentReceiptItem` - строки чека: источник строки, название, количество, цена, сумма, НДС, предмет расчета, способ расчета, единица измерения, SKU/штрихкод.
- Фискальные настройки филиала в `ShopSettings`: включение фискализации, СНО, НДС товаров и услуг по умолчанию.
- Фискальные настройки номенклатуры в `InventoryItem`: предмет расчета, НДС, единица измерения.
- Фискальные настройки доп. услуг в `AdditionalService`: предмет расчета, НДС, единица измерения.
- `PaymentMethod.fiscal_payment_type` отделяет наличные, электронные, зачет аванса, кредит и прочие формы оплаты.

### Поток оплаты заказа

1. Пользователь создает платеж по заказу.
2. CRM проверяет остаток к оплате и доступ к филиалу.
3. Если у филиала включена фискализация, CRM до изменения `order.prepayment` собирает чек.
4. Полная оплата без авансов идет itemized: ремонт + доп. услуги, скидка распределяется пропорционально.
5. Частичная предоплата идет отдельной строкой `Предоплата по заказу ...`.
6. Финальный расчет после ранее пробитого аванса строит полноценный ККМ-чек с itemized строками на весь заказ и платежами `electronic/cash + prepaid`.
7. Для эквайрингового receipt в payment request CRM не отправляет чек, если сумма чека отличается от суммы списания. Такой случай надо отправлять как отдельный closing/final-settlement чек через ККМ/провайдера, иначе payload будет юридически неверным.

### Поток POS-продажи

1. Платеж должен совпадать с итогом розничной продажи.
2. CRM собирает чек из `RetailSaleItem`.
3. НДС и предмет расчета берутся из товара, если заполнены, иначе из настроек филиала.
4. Скидка продажи распределяется по строкам пропорционально.

### Провайдеры

Сейчас есть адаптеры:

- `receipt_snapshot_to_yookassa`
- `receipt_snapshot_to_tbank`
- `receipt_snapshot_to_sber`

Адаптеры валидируют ограничения провайдера и не молча подменяют неподдерживаемые значения. Например, YooKassa не принимает все признаки способа расчета в payment receipt, поэтому такие случаи должны идти отдельным ККМ-чеком.

## Миграция из других CRM

Добавлен отдельный слой `data_import`, чтобы импорт был идемпотентным и проверяемым:

- `MigrationSource` - источник данных: другая CRM, CSV, выгрузка SQL.
- `ImportBatch` - один dry-run или импорт.
- `StagedImportRecord` - сырые строки до создания бизнес-сущностей.
- `ExternalRecordLink` - стабильная связь `source + entity_type + external_id -> объект CRM`.
- `ImportIssue` - ошибки и предупреждения preflight/import.

### Production-flow миграции

1. Сначала только dry-run через `/api/data-import/preflight`.
2. Перед dry-run запросить `/api/data-import/flow`: он возвращает порядок сущностей,
   обязательные поля и sample payload для клиента, устройства, склада, заказа и платежа.
3. CRM проверяет обязательные поля, дубли внешних ID, уже импортированные записи, неизвестные типы сущностей.
4. Все external ID остаются в `ExternalRecordLink`, а не засоряют модели заказов/клиентов/товаров.
5. Повторный импорт той же записи должен быть update/idempotent, а не создание дубля.
6. До фактического импорта нужно прогнать минимум сущности в порядке: customers -> devices -> inventory items -> orders -> payments.
7. История preflight-пакетов доступна через `/api/data-import/batches`.
8. После импорта сверить контрольные суммы: количество клиентов, заказов, платежей, сумма оплат, сумма остатков, список ошибок.

## Что важно перед боевым включением ККМ

- Подтвердить с бухгалтером клиента СНО, НДС и сценарии аванс/предоплата/полный расчет.
- Для YooKassa/T-Bank/Sber прогнать sandbox: полная оплата, частичная предоплата, финальный расчет с зачетом аванса, возврат.
- Проверить, что в CRM у клиентов есть email или телефон для электронного чека при онлайн-оплате.
- Запретить оплату при включенной фискализации, если CRM не может подготовить корректный чек.
